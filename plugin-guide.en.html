Little LUMI plugins — first steps

It is fine if you have never written code. Follow this page from the top and within thirty minutes Lumi will be saying the words you gave her.

Step 0 — starting from nothing

This section is for someone who has never programmed. You do not need to know what a command prompt is, or what "compile" means. Click and type what is written below and you will be done in thirty minutes. If you already use a command prompt, skip this section and start at What you need.

What you will do today. A plugin is a small program that adds something to Lumi. Today you will not write code — you will take an example plugin that is already written and shipped inside the SDK, build it, put it into Lumi, and have Lumi greet you on startup. At the very end you will change that one greeting line. That is the whole skeleton of making a plugin; every other section is just that one line getting longer.

What you need. A Windows PC, Little LUMI Model bought on Steam, and an internet connection. You will install two new programs (JDK 25 and Python 3). Both are free, and neither touches anything but Lumi.

How to read this Take the eight steps below in order. Each one has what to do · what success looks like · if it does not work. If you cannot see "what success looks like", do not move on — read "if it does not work" right where you are. Carrying an unfinished step forward makes the error messages in the later steps impossible to understand.

  1. Opening a command prompt

    The commands in this guide are typed into a black window called the command prompt. It is the window where you give the computer work in writing.

    What to do. Press the Windows key (the one with the window on it), type cmd, and press Enter. A black window appears.

    What success looks like. The window holds a line like C:\Users\yourname> with a cursor blinking after it. That line is called the prompt: type one line there, press Enter, and that command runs. Try this one — if a list of the files in the current folder scrolls past, the window is working.

    dir

    Four things you must know.

    • Change folder with cd. Type cd C:\LumiSDK and the prompt line becomes C:\LumiSDK>. Commands after that run inside that folder. To move to another drive, type just the drive letter first, like D:, and press Enter.
    • Wrap a path that has spaces in double quotes. cd "C:\Program Files (x86)\Steam" — leave the quotes out and it cuts at the space and says "The system cannot find the path specified."
    • Paste with the right mouse button. Press the Copy button at the top right of a code box on this page, then click once with the right mouse button inside the black window and it lands there (Ctrl+V works too). Do not retype commands by hand — typos are most of what goes wrong.
    • To close the window type exit or press the X at its top right. Closing the window does not undo what you have done.

    If it does not work. If pressing the Windows key opens no search box, click the Start button at the bottom of the screen with the mouse and type command prompt. If the window opens but every command answers "is not recognized as an internal or external command", that is still normal — you have not installed anything yet. The next step installs it.

  2. Install JDK 25 — the tool that builds Java code

    Plugins are written in Java. Turning Java code a person can read into a jar file a computer can read is called building (compiling), and the tool for it is the JDK. Lumi carries a Java of its own, but that one only runs code; it cannot build it.

    What to do. Go to adoptium.net and pick Temurin 25 · Windows · x64 · JDK · .msi (JDK, not JRE). Double-click the downloaded file to install it. On the Custom Setup screen that appears while you click "Next", click the icons on the two lines "Set JAVA_HOME variable" and "Add to PATH" and change them to "Will be installed on local hard drive". They are off by default (marked with an X), and skipping past them means the commands will not work later.

    What success looks like. When the install finishes, close the command prompt and open a new one (the settings only apply to new windows). Then type this.

    javac -version
    this means it worked (the trailing digits may differ)javac 25.0.4

    If it does not work. "'javac' is not recognized as an internal or external command, operable program or batch file" has three causes. ① You did not open a new command prompt — close the window and open it again. ② You did not switch the two options on during the install — run the .msi again, choose Change, and switch them on. ③ You downloaded the JRE instead of the JDK — download again. If the number comes out lower than 25, like javac 21, an older Java is being found first; install 25 and check again.

  3. Install Python 3 — the tool that does the building for you

    The SDK's build tool (build_plugin.py) and test tool (run_tests.py) are written in Python. You will never write Python; it is only needed to run those tools.

    What to do. On python.org/downloads press the yellow "Download Python 3.x" button. Double-click the downloaded file: at the very bottom of the first screen there is a checkbox "Add python.exe to PATH". Switch it on and press "Install Now".

    What success looks like. Close the command prompt, open a new one again, and type this.

    python --version
    this means it workedPython 3.13.5

    If it does not work. If a Microsoft Store window opens or you get "Python was not found", it is not installed yet. Windows carries a stub that opens the Store under the name python even before Python is installed. Run the install again, with "Add python.exe to PATH" switched on. If you definitely installed it and the Store still opens, go to Settings → Apps → Advanced app settings → App execution aliases, switch off python.exe and python3.exe, and open a new command prompt.

  4. Download and unpack the Mod SDK

    It is a zip file holding everything you need to build a plugin.

    What to do. On the Little LUMI SDK downloads page pick the release of the same version as the Lumi you run, and under Assets download LittleLUMI-ModSDK-1.3.0-…zip (as of this guide the app and the SDK are both 1.3.0). In Explorer, right-click the zip → Extract All. A short path with no spaces and no non-English characters is easiest — below we will use C:\LumiSDK.

    When it is unpacked, C:\LumiSDK looks like this at the top level.

    C:\LumiSDK\ ├─ lib\ ← the Lumi jars, for building only. You cannot run Lumi with these ├─ tools\ ← build_plugin.py (build) · run_tests.py (test without the app) · pack_workshop.py (check before a Workshop upload) ├─ docs\ ← API.en.md (what you can do) · CATALOG.en.md (the identifiers) · CHANGELOG.md ├─ examples\hello\ ← the example plugin you will use today ├─ examples\plugin-transformer\ ← an advanced example. Not used today ├─ plugin-guide.en.html ← this document ├─ README.en.md ← the one-page summary ├─ LICENSE-SDK.txt ← the terms of use └─ sdk.json ← the version information for this SDK

    What success looks like. Type these two lines in the command prompt, one after the other. The names above should appear in the listing.

    cd C:\LumiSDK
dir

    If it does not work. If the listing shows a single LittleLUMI-ModSDK-… folder instead of lib · tools, everything sits one level deeper. Either drag the contents of that folder up into C:\LumiSDK, or cd into that folder from now on. If lib\Shimeji-ee.jar is missing, the zip was not fully extracted — extract it again.

  5. Build the example — your first command

    Now you build. All you do is hand the example folder examples\hello to the tool.

    What to do. These two lines in the command prompt.

    cd C:\LumiSDK
python tools\build_plugin.py examples\hello

    What success looks like. After a few seconds a line starting with built: appears. The jar has been created at the place that line names (the numbers in brackets may differ from version to version).

    this means it workedbuilt: C:\LumiSDK\dist\hello.lumi.sample\plugins\hello.lumi.sample.jar  (hello.lumi.sample, 2 source(s), 4 resource(s))
done: copy C:\LumiSDK\dist\hello.lumi.sample into the game as mods\<name> and restart

    If it does not work. javac not found means step 2 is unfinished — check javac -version again, or point at it directly like this.

    python tools\build_plugin.py examples\hello --javac "C:\Program Files\Eclipse Adoptium\jdk-25.0.4.7-hotspot\bin\javac.exe"

    If the Store window opens, step 3 is unfinished. plugin.json missing: … means you typed the folder name wrong — check the spelling of examples\hello. can't open file …build_plugin.py means you typed it somewhere other than C:\LumiSDK — start again from cd.

  6. Put it into Lumi and check

    Installing means putting the built jar into Lumi's mods\ folder. Copying is all there is; there is no installer to run.

    What to do ① close Lumi. Press the ^ next to the clock at the bottom right to open the tray, right-click the Lumi icon and choose Quit. While Lumi is running its files are locked and the copy is refused.

    What to do ② open the Lumi folder. In the Steam library, right-click Little LUMI Model → Manage → Browse local files. That is the window where you can see the mods\ folder.

    What to do ③ copy. Open a second Explorer window and go to C:\LumiSDK\dist. Drag the whole hello.lumi.sample folder into the mods\ folder of the Lumi folder. The result must look like this.

    <LUMI folder>\mods\ └─ hello.lumi.sample\ └─ plugins\ └─ hello.lumi.sample.jar

    What to do ④ run it. Start Lumi again from Steam (plugins are read once, at startup).

    What success looks like. Any one of these three is enough.

    • Lumi appears and a moment later her bubble says "Luba! (plugin)". If the app language is Korean it is 「루바! (플러그인)」.
    • If you missed the greeting, right-click the Lumi icon in the tray. A new row "Hello LUMI: say hi" is there, and pressing it makes Lumi say a line.
    • Tray → Settings → the Mods tab shows a hello.lumi.sample row with a "plugin" chip. Press Details on that row and the two settings the example declares ("Greet when the app is up" · "Greeting mood") are drawn right inside Lumi's own window.

    If it does not work. If the Mods tab has no row at all, you put the jar directly under mods\ — a row appears for each folder under mods\, and loose files are ignored. If the row is there but carries a "files" chip instead of "plugin", the folder depth is wrong; check that the jar sits inside mods\hello.lumi.sample\plugins\. If the row is there and says "could not be loaded", open <LUMI folder>\app\LittleLumiLog0.log.0 in Notepad and look for lines containing Plugin. A table by symptom is in When it does not work.

  7. Change one line

    Now make the greeting yours. You are not editing Java code, just one line of a text file.

    What to do ①. Open C:\LumiSDK\examples\hello\src\plugin_en.properties in Notepad or VS Code. It has a line like this.

    examples\hello\src\plugin_en.propertiesgreeting=Luba! (plugin)

    Change only what is to the right of =, and save as UTF-8 (in Notepad, pick UTF-8 under "Encoding" at the bottom of the save dialog).

    after the editgreeting=This is my own greeting

    What to do ②. Quit Lumi. While it runs the jar is locked and overwriting is refused — forgetting this is the most common cause of "I changed it and nothing changed".

    What to do ③. Build again and overwrite the new jar in the same place as before.

    cd C:\LumiSDK
python tools\build_plugin.py examples\hello

    Copy C:\LumiSDK\dist\hello.lumi.sample\plugins\hello.lumi.sample.jar to <LUMI folder>\mods\hello.lumi.sample\plugins\ and choose "Replace". If copying every time is tiresome, add --out to the build command and it will build straight into that place.

    python tools\build_plugin.py examples\hello --out "<LUMI folder>\mods\hello.lumi.sample\plugins"

    What to do ④. Start Lumi again.

    What success looks like. The bubble shows the new words you wrote.

    If it does not work. If the old words are still there, either ① you overwrote without quitting Lumi and the copy silently failed, ② you did not save the file before building, or ③ you copied it into a different folder. If the letters come out as ??? or broken symbols, you did not save as UTF-8 — save again and build again.

  8. Where to go from here

    Well done. You have gone once round the loop of build · install · change. However big the plugins you make get, that loop stays the same. Read on in this order.

    • What a plugin is — what it was that you just did.
    • Your first plugin — building your own folder from scratch instead of an example. The quick way is to copy the whole examples\hello folder, rename it to my-plugin, change the id and name in its plugin.json to yours, and type python tools\build_plugin.py my-plugin.
    • What you can do · Examples — speaking, behaviours, timers, menus, settings rows.
    • Changing decisions with hooks · Data mods go in fragments — reaching into Lumi's decisions and data.
    • Sharing it — when it is done, put it on the Workshop.
    • When it does not work · Glossary — whenever you get stuck.

Building it with an AI tool

Even without knowing Java you can have a coding assistant AI such as Claude Code or Codex build a plugin for you. One thing must be clear, though. The AI writes the code, but handing it to other people is your responsibility. A plugin runs inside the same program as Lumi with your account's rights, and the people who install it are trusting you. Do not release code you do not understand.

Even when the AI does the work, steps 2, 3 and 4 of Step 0 (JDK 25 · Python 3 · unpacking the SDK) have to be done by a person first. AI tools usually will not install those for you.

What to hand it

  • With a tool that can see a whole folder (the kind that runs in a command prompt), the best thing is to open C:\LumiSDK as its working folder. Then the AI reads the docs and examples itself, and can run the build and test commands on its own.
  • With a tool where you only paste text, give it these four: docs\API.en.md (everything you can do) · docs\CATALOG.en.md (the names of behaviours, events, hooks and settings keys) · examples\hello\plugin.json · examples\hello\src\hello\HelloPlugin.java. If the docs are too long to fit, at least include docs\API.en.md — without it the AI invents methods that do not exist.

A first prompt to paste

Copy the text below as it is and replace only the <…> part with your own words. The constraints listed are the ones that actually go wrong most often.

a first prompt for the AII want to make a plugin for Little LUMI Model. The working folder is this Mod SDK folder.

First read docs\API.en.md and docs\CATALOG.en.md, and use examples\hello as the model.

What to make: <one or two sentences about what you want. For example: every 30 minutes Lumi
suggests a stretch, and she stays quiet while Focus Mode is on>

Rules to follow:
- It is compiled with JDK 25. Java 25 syntax is fine.
- Make a new folder my-plugin with the same structure as examples\hello:
  plugin.json (at the top of the folder) / src\<package>\*.java /
  src\META-INF\services\com.group_finity.mascot.lumi.plugin.LumiPlugin
- That services file holds one line: the full name of the entry class (e.g. my.plugin.MyPlugin).
  It is not the file where the plugin.json id goes.
- The id in plugin.json uses only lower-case letters, digits, dots, hyphens and underscores,
  and starts with a lower-case letter or a digit. api_version is 1 and app_version is 1.3.0.
  The id becomes the data folder name, so do not change it later.
- Reach app features only through PluginContext (ctx). Do not call app classes that are not in
  docs\API.en.md, and do not go digging with reflection.
- If you need to change a decision the app makes, answer it with ctx.hook(...). Do not use
  bytecode transformation (ctx.patch · ctx.onLoad · LumiTransformer).
- Never block a promise the user made themselves (alarms, an errand they pressed for).
- Keep my settings in ctx.prefs(). Do not store passwords or API keys.
  If it uses the internet, set network to true in plugin.json.
- Put at least one test in test\*.java using PluginTestKit.
- Build with python tools\build_plugin.py my-plugin, test with python tools\run_tests.py my-plugin.
  Keep fixing until both commands pass.
- Do not invent things. Use only the methods, event topics, hook names and behaviour names that
  are in docs\API.en.md and docs\CATALOG.en.md, and if something you need is not in the docs, say so.

The checks a person has to do

The AI saying "it is all done" is not a check. Do these five with your own hands.

  1. It builds. python tools\build_plugin.py my-plugin must end with a built: … line. If error text is mixed in, it is not done yet.
  2. The tests pass. python tools\run_tests.py my-plugin must end with OK: N test class(es) passed. If you see FAILED:, hand that line back to the AI as it is.
  3. It really works in the app. Quit Lumi, put the jar into mods\<name>\plugins\, start it again, and see it with your own eyes. The AI cannot start Lumi, so this is the one step it cannot do for you.
  4. The log is clean. Open <LUMI folder>\app\LittleLumiLog0.log.0 and look for your id. Plugin loaded: <your id> must be there, with no start() failed and no warning line carrying your id.
  5. You read the code once. Check that nothing deletes files or sends them out, and that network and affects_character in plugin.json match what it actually does. If there is code reading another plugin's folder (plugindata\<someone else's id>\), delete it. If you cannot judge, read Rules and cautions and use that as your measure.
Careful AI invents plausible-sounding methods and hook names that do not exist. If the code has a ctx. call you have not seen before, look that name up in docs\API.en.md. If it is not there, it will either fail to build or — worse — build fine and then do nothing at all in the app.

What a plugin is

There are two kinds of mod for Little LUMI.

  • Data mods — changing artwork, lines and behaviour configuration files. No code is needed; you put files into the mods\ folder and that is it. How to do it is in mods\Mods Guide.txt in the install folder.
  • Plugins — running a small program (Java code) inside Lumi. That is what this page is about. It can make Lumi speak, make her act, listen to what she is doing, run timers, and read and write files. Nearly anything the Lumi app can do, it can do.

One plugin is one jar file. Inside it are the code you wrote and a plugin.json saying "this is who the plugin is and what it does". At startup Lumi reads every jar in the plugins\ folders and shows what got loaded on the Mods tab of the settings window.

The flow Make a folder → write three files → build with two lines of command → put it in mods\ → run Lumi. That is all of it.

What you need

  1. Install JDK 25

    To build Java code into a jar you need the JDK (Java Development Kit). The one inside Lumi only runs code (a JRE) and cannot build. Download Temurin 25 (Windows x64, .msi) from adoptium.net and install it. Switching on "Set JAVA_HOME" and "Add to PATH" on the install screen makes life easier.

    To check it installed: open the command prompt from the Start menu and type this.

    javac -version

    Something like javac 25.x.x means you are ready. "is not recognized as an internal or external command" means the PATH option was not switched on. Install again, or open a new command prompt.

  2. Install Python 3

    The SDK's build tool (build_plugin.py) and test tool (run_tests.py) are written in Python. Download Python 3 from python.org and install it, and be sure to switch on "Add python.exe to PATH" on the first screen of the installer.

    To check: open a new command prompt and type this.

    python --version

    Something like Python 3.x.x means you are ready. Windows has a command called python even before Python is installed, but it is a stub that opens the Microsoft Store — if a Store window opens or you get "Python was not found", it is not installed yet.

  3. Get the Mod SDK

    Plugins are built with the Mod SDK — the Lumi jars to compile against, the build tool, the examples and the API docs, all in one zip (see The Mod SDK). Download it and unpack it anywhere. For example C:\LumiSDK. Below we call it <SDK folder>.

  4. A text editor

    Notepad will do, but VS Code (free) is better. It saves files as UTF-8 and colours Java syntax for you. If you use Notepad, pick UTF-8 as the encoding when you save.

  5. Find the Lumi install folder

    In the Steam library, right-click Little LUMI Model → Manage → Browse local files. The folder that opens looks like this.

    Little LUMI Model\ ├─ Little LUMI.exe ← the executable ├─ mods\ ← where mods and plugins go │ └─ Mods Guide.txt └─ app\ ← Lumi itself ├─ Shimeji-ee.jar ← the Lumi jar (the same one is in the SDK's lib\) ├─ lib\ ← the libraries Lumi uses ├─ plugindata\ ← each plugin's own data folder (plugindata\<id>\). A mod's jar is read straight from mods\ └─ LittleLumiLog0.log.0 ← the log. Start here when something goes wrong

    Copy that folder's address somewhere. Below we call it <LUMI folder>. For example: C:\Program Files (x86)\Steam\steamapps\common\Little LUMI Model

Your first plugin

A plugin that says "Hi! I'm your first plugin" when Lumi appears, says two lines in turn when you double-click her, and writes a log line every time she changes behaviour. You make three files and type one command.

  1. Make the folder

    Anywhere will do. For example C:\LumiPlugins\hello. Inside it, make folders and files in this shape.

    C:\LumiPlugins\hello\ ├─ plugin.json ← the name tag (at the top of the plugin folder) └─ src\ ├─ hello\ │ └─ HelloPlugin.java ← the code └─ META-INF\ └─ services\ └─ com.group_finity.mascot.lumi.plugin.LumiPlugin ← a file with no extension. The entry point's name

    The SDK's examples\hello\ is exactly this shape. You can copy that whole folder and just rename it to start.

    Careful The last file has no extension. When you save it from Notepad, wrap the name in double quotes as "com.group_finity.mascot.lumi.plugin.LumiPlugin" and no .txt will be added. Switching on "File name extensions" in Windows Explorer makes this easy to verify.

  2. plugin.json — the name tag

    Write this in the plugin.json at the top of the plugin folder. The id has to be unique in the world, so name it like yournick.pluginname. Only lower-case letters, digits, dots, hyphens and underscores are allowed.

    plugin.json{
  "id": "mynick.hello",
  "name": "Hello LUMI",
  "version": "1.0.0",
  "author": "my nickname",
  "description": "Greets you when Lumi appears, and logs every behaviour change.",
  "dependencies": [],
  "api_version": 1,
  "app_version": "1.3.0",
  "affects_character": false,
  "network": false
}
    FieldWhat it means
    idThe unique name. It is also used as the data folder name and the jar name. Changing it later makes it a different plugin, so choose well the first time.
    name · version · author · descriptionShown as they are on the Mods tab. The version is in the 1.0.0 shape.
    dependenciesThe ids of other plugins that must load first. If one of them is not loaded, your plugin does not load either and the tab shows "needs another plugin".
    api_version1 as of this guide.
    app_versionThe app version you tested against. When the running app differs, the Mods tab shows a chip such as "made for 1.3.0" — information only, it never blocks.
    affects_charactertrue if it changes Lumi's behaviour or her lines. The tab marks it "changes behaviour".
    networktrue if it uses the internet. The tab marks it "uses the internet". It is there to tell the user honestly.

  3. HelloPlugin.java — the code

    src\hello\HelloPlugin.java. Copy it as it is even if some of the words are new. They are unpacked one by one in What you can do below.

    src\hello\HelloPlugin.javapackage hello;

import com.group_finity.mascot.lumi.plugin.LumiPlugin;
import com.group_finity.mascot.lumi.plugin.PluginContext;

public final class HelloPlugin implements LumiPlugin {

    @Override
    public void start(PluginContext ctx) {
        // "ready" comes once, after Lumi and the engine are fully up. Greet then.
        ctx.on("ready", event -> ctx.say("Hi! I'm your first plugin", 4000));

        // Double-clicking Lumi says two lines in turn. sayQueued shows the next one after the first ends.
        ctx.on("doubleclick", event -> {
            ctx.sayQueued("Did you call?", 2500);
            ctx.sayQueued("I'm right here!", 2500);
        });

        // Comes every time Lumi changes behaviour. Leaves one line in the log file.
        ctx.on("behavior", event ->
                ctx.log().info(event.get("imageSet") + " started " + event.get("name")));
    }

    @Override
    public void stop() {
        // Called when Lumi shuts down. Anything to tidy up goes here.
    }
}

  4. The entry point file

    src\META-INF\services\com.group_finity.mascot.lumi.plugin.LumiPlugin holds exactly one line: the full name of your class. That file is how Lumi knows which class to wake.

    src\META-INF\services\com.group_finity.mascot.lumi.plugin.LumiPluginhello.HelloPlugin

  5. Build — one line of command

    Open a command prompt, go to <SDK folder> and type one line. It compiles against the SDK's lib\ and packs the jar with plugin.json and the entry point file included.

    cd <SDK folder>
python tools\build_plugin.py C:\LumiPlugins\hello

    A line built: …\dist\mynick.hello\plugins\mynick.hello.jar means it worked. The jar name follows the id in plugin.json. If red text appears, see When it does not work.

    Tip With --out you can build straight into the Lumi folder: python tools\build_plugin.py C:\LumiPlugins\hello --out "<LUMI folder>\mods\hello\plugins". If javac is not on the PATH, point at it like --javac "C:\Program Files\Eclipse Adoptium\jdk-25…\bin\javac.exe". If typing it every time is tiresome, save the line as build.bat and double-click it.
    Building by hand, without the tools

    The JDK's javac and jar alone are enough. From the plugin folder, with <LUMI folder> replaced by yours, two lines:

    javac --release 25 -encoding UTF-8 -cp "<LUMI folder>\app\Shimeji-ee.jar;<LUMI folder>\app\lib\*" -d out src\hello\HelloPlugin.java
jar --create --file mynick.hello.jar -C out . plugin.json -C src META-INF

    The only difference is compiling against the install folder's jar instead of the SDK's; the jar that comes out is the same.

  6. Install it

    Make your mod folder under Lumi's mods\ and put the jar in the plugins\ inside it. If you used --out while building, it is already there.

    <LUMI folder>\mods\ └─ hello\ └─ plugins\ └─ mynick.hello.jar

    Every time it starts, Lumi lays the folders in mods\ over app\ (data such as artwork and configuration). Jars in plugins\ are not copied; they are read straight from the mod folder. Even if Steam verifies the files and puts them back, the next run lays it over again, so there is nothing to worry about.

  7. Run it and check

    If Lumi is already up, quit from the tray and start again (plugins are read only at startup). If Lumi appears and a moment later her bubble says "Hi! I'm your first plugin", that is it! Click her twice quickly and "Did you call?" "I'm right here!" follow one after the other.

    Two places to check:

    • Right-click the tray → Settings → the Mods tab. Your mod's card is there. Press "Details" and the plugin's state appears, with the reason written there if there is a problem.
    • <LUMI folder>\app\LittleLumiLog0.log.0. Open it in Notepad and look for Plugin loaded: mynick.hello. Click Lumi to make her change behaviour and the log lines you wrote pile up too.

What you can do

The ctx (PluginContext) you get in start() is the door through to Lumi. The tables in this section do not separate stable entries from experimental ones — a fair share of the doors listed below are still "experimental", so they may change or disappear even within the same api_version. Which is which is in the table in docs\API.en.md (the "experimental" chip after the name) and in §8 "Compatibility policy". The full list with exact arguments is in the Mod SDK's docs\API.en.md §3, and the identifiers (behaviours, events, hooks, settings keys) are in docs\CATALOG.en.md.

Speaking

How to call itWhat it does
ctx.say("line", 4000)Shows text in the bubble of the character who last spoke. The second number is milliseconds (4000 = 4 seconds; 0 or less means the default length). A line already showing is replaced at once.
ctx.sayFor("Lumi", "line", 4000)Makes a particular character (by image set folder name) speak.
ctx.sayQueued("line", 3000) · ctx.sayQueuedFor("Lumi", "line", 3000)Queue it. It comes in turn after the current line goes down (up to 20 lines). Use this for lines that have an order, such as Pomodoro announcements. ctx.clearQueue() empties your own queue and ctx.queueLength() is the total number waiting.
ctx.ask("question", List.of("Rock", "Paper", "Scissors"), 10000, i -> …) · ctx.askFor("Lumi", …)A bubble with choices. Two to four buttons appear below the question. When the user picks one, i gets its number (from 0). -1 means it appeared but got no answer (timed out, Esc, the character went away); -2 means the app took it back — a question already showing can be taken back too (you called a new ask that replaced it · clearQueue() · it waited too long in the queue · the queue is full). Only one bubble shows at a time and another plugin's question waits its turn — your new question replaces only your own old one and never pushes anyone else's aside. The time limit (third argument) counts from the moment it appears, and the longest it may wait in the queue is given as a fourth argument before the callback (ctx.ask("question", options, 10000, 5000, i -> …); 30 seconds if you leave it out). The answer also goes out as a choice event.
ctx.hideBubble() · ctx.showBusy("Lumi")Take the bubble down · show the "···" thinking mark (the next line replaces it).

Examples

Try putting these inside the start() of your first plugin. Building and installing works the same way.

Speaking on a particular behaviour

ctx.on("behavior", event -> {
    if ("SitDown".equals(event.get("name"))) {
        ctx.sayFor((String) event.get("imageSet"), "I'll rest a bit", 3000);
    }
});

A behaviour every five minutes

ctx.every stops by itself when Lumi shuts down. The first number is how long to wait the first time, the second is the period (in milliseconds).

ctx.every(5 * 60 * 1000, 5 * 60 * 1000, () -> ctx.behave("HappyHop"));

Counting and saving

Values you keep in ctx.prefs() survive to the next run.

ctx.on("headpat", event -> {
    int n = ctx.prefs().getInt("pats", 0) + 1;
    ctx.prefs().set("pats", n);
    if (n % 10 == 0) ctx.say("That's " + n + " head pats already!", 3000);
});

For bigger data, use a file in ctx.dataDir() instead of the settings.

java.nio.file.Path diary = ctx.dataDir().resolve("diary.txt");
java.nio.file.Files.writeString(diary, "Another day with Lumi\n",
        java.nio.charset.StandardCharsets.UTF_8,
        java.nio.file.StandardOpenOption.CREATE, java.nio.file.StandardOpenOption.APPEND);

Rock, paper, scissors with choices

ctx.on("doubleclick", event -> {
    java.util.List<String> hands = java.util.List.of("Rock", "Paper", "Scissors");
    ctx.ask("Rock, paper, scissors!", hands, 10000, picked -> {
        if (picked < 0) return;                      // -1 = no answer (timed out, Esc), -2 = the app took it back
        int mine = new java.util.Random().nextInt(3);
        boolean win = (picked - mine + 3) % 3 == 1;
        ctx.sayQueued("Lumi picks " + hands.get(mine) + "!", 2000);
        ctx.sayQueued(win ? "I lost…" : picked == mine ? "A tie" : "Lumi wins!", 2500);
        if (win) ctx.awardAffection("rps", 1);
    });
});

Seeing where a character is

ctx.every(1000, 1000, () -> {
    for (com.group_finity.mascot.lumi.plugin.MascotState m : ctx.mascots()) {
        ctx.log().fine(m.imageSet() + " #" + m.id() + " feet " + m.anchor()
                + (m.lookRight() ? " →" : " ←") + " " + m.behavior());
    }
});

Using other libraries

You cannot put files into Lumi's lib\ (a protected folder). Put the libraries you need inside your own jar (a fat jar), or in plugins\lib\ in the mod folder — Lumi puts the jars in that folder on the class path too. If the same class is in two jars, the one lower in the mod order wins.

Rules and cautions

  • A plugin runs inside the same program as Lumi, with your account's rights. It can do anything you can. That is exactly how much the user trusts you when they install it. Do not read the user's files carelessly or send them anywhere. In particular, another plugin's app\plugindata\<id>\ (for example LUMI Chat's plugindata\lumi.ai\ — the AI keys and conversation memory) belongs to the user alone.
  • An exception stops inside your plugin. If start() throws, only that plugin becomes "could not be loaded" and Lumi still comes up. An exception inside an event function is only logged.
  • The screen (Swing) belongs to the EDT. Use SwingUtilities.invokeLater(() -> …) when making or changing a window. Touching them directly from event functions and timer threads occasionally draws oddly.
  • You cannot shadow Lumi's own classes. The Lumi jar always comes first. Putting a class of the same name in your jar still uses Lumi's. If you want to change the app itself, ctx.patch(className, ClassFileTransformer) can rewrite bytecode while it runs (ASM is in Lumi's lib\; other libraries such as ByteBuddy go in your own jar). The Steam gate, the offline token, the feature locks, the plugin loader, the Steam integration, the affection store and the achievement classes are refused.
  • Files the launcher protects. Through mods\ you cannot overwrite Lumi itself (the jar, the jre, lib), the Steam-related files, or the user's settings and record files. The full list is in mods\Mods Guide.txt. Refused files are written to %TEMP%\littlelumi_launch.log.
  • Switching on and off. The user can switch each mod folder, and each plugin, on and off from the Mods tab. Both switching on and switching off take effect from the next launch (nothing is loaded or unloaded while it runs), and a changed row gets "Applies at next launch". Running Lumi with --no-plugins loads nothing (you can put that in the Steam launch options).
  • The order rule is "lower wins". The Mods tab shows Workshop subscriptions and your own mods in one list, and you reorder with the grip (≡) on the left of a row or the ▲▼ buttons (pressing "Details" unfolds the path, the plugin state and the buttons). They are applied from top to bottom, so a mod lower down overrides the same file and the same plugin id. A mod that overlaps nothing says "Shares no file with another mod, so its place in the order changes nothing". The order is saved in mods\order.txt.
  • An update is visible to the user. When the jar changes, the tab marks it "changed since last run". Please raise the version.

Sharing it

As a zip

If you depend on libraries, you do not have to merge them into your jar — you can put them separately in plugins\lib\. Lumi puts the jars in that folder on the class path too.

Zip up the whole mods\hello\ folder. The person receiving it unpacks it into their own mods\, starts Lumi again, and that is it. You can put a page of notes (readme.txt) in the mod folder as well. Loose files directly under mods\ are ignored, so nothing gets messy.

On the Steam Workshop

If a Workshop item has a plugins\ folder, Lumi recognises it as a "plugin item" and puts it into the subscriber's mods\workshop-<number>\ automatically. Subscribed code mods are off by default. Enable the checkbox in Settings → Mods and accept the risk notice; code and data then apply on the next app start. Changes to JARs or dependency libraries require consent again. The item folder only has to be the same shape as a mod folder.

hello-workshop\ ├─ plugins\mynick.hello.jar ├─ plugins\plugin.json ← nice to have (for the item page). The one inside the jar is the real one ├─ plugins\lib\*.jar ← libraries you depend on └─ img\…, conf\… ← you may carry data along too

The kinds of file that come through the Workshop are fixed: .png .xml .txt .wav .tsv .properties .json .ttf .otf. To that come three exceptions decided by place — .jar and .json directly under plugins\, .jar in plugins\lib\, and .py directly under tools\ (helper scripts the app does not run). Those three pass only in plugin and mod items; in character (image set) and voice pack items they are dropped even in the right place. Other files (executables and so on) do not reach subscribers. Language packs (conf\language_ko.properties), fonts, island layouts (islands.json) and the LLM provider list (conf\llm_providers.txt) all fall inside this.

The easiest way is to upload from inside Lumi. Tray → Settings → the Mods tab, press "Upload to Workshop" on your mod's row, and that folder becomes the item as it is (you only fill in the title, the description and the preview image). Once uploaded, the button on the same row becomes "Update on Workshop" and you use that from then on (the item number is written into workshop-upload.txt). Steam has to be running.

Run tools\pack_workshop.py once before you upload. The app leaves out files that do not match the rules silently, with no error — which is why "I uploaded it but some files did not go" is something the subscribers find out first. This tool applies the same rules as the app in advance, tells you the item kind (plugin · mod · character · voice pack), lists the files that will be dropped with the reason, and builds an upload folder holding only what matches the rules plus a starting item.vdf.

python tools\pack_workshop.py C:\LumiPlugins\hello-workshop --check
python tools\pack_workshop.py C:\LumiPlugins\hello-workshop

--check only checks and creates nothing. Run it plainly and you get the filtered folder dist\workshop\<name>\ and, beside it, <name>-item.vdf (--out changes where).

If you would rather upload from the command line without Steam, SteamCMD works too. It is a little fiddly the first time only.

  1. Download SteamCMD and unpack it anywhere.
  2. Agree once to the Workshop terms with your Steam account.
  3. Make an item.vdf. If you ran pack_workshop.py above, <name>-item.vdf already exists and you only fill in title and previewfile. Writing it by hand, copy the one below. contentfolder and previewfile are absolute paths, and the preview is a 512×512 PNG. For a first upload, set publishedfileid to 0.
item.vdf"workshopitem"
{
    "appid"            "5075020"
    "publishedfileid"  "0"
    "contentfolder"    "C:\\LumiPlugins\\hello-workshop"
    "previewfile"      "C:\\LumiPlugins\\hello-preview.png"
    "visibility"       "0"
    "title"            "Hello LUMI plugin"
    "description"      "Greets you when Lumi appears. A plugin item — subscribe and it loads from the next launch."
    "changenote"       "First upload"
}
steamcmd +login yoursteamlogin +workshop_build_item C:\LumiPlugins\item.vdf +quit

Once it is up, SteamCMD tells you the item number. Put that number in publishedfileid and from then on the same command updates that item. You can also edit the description on the item page. Please do write "what the plugin does" and "whether it uses the internet" in the item description. That is what users choose by.

The Mod SDK

The Mod SDK used in Your first plugin is a single zip. This is what is in it.

LittleLUMI-ModSDK-<app version>-<build>\ ├─ lib\ ← compile-only jars (Lumi itself + libraries). They will not run without Steam ├─ tools\build_plugin.py ← building a plugin (the tool used in your first plugin) ├─ tools\run_tests.py ← building and running your plugin's test\*.java (PluginTestKit) ├─ tools\pack_workshop.py ← the check before a Workshop upload + the filtered folder and a starting item.vdf ├─ docs\API.en.md ← the public API reference (API.md is the Korean one) — the stable/"experimental" marks and "Compatibility policy". CATALOG.en.md = the tables of behaviours, events, hooks and settings keys, CHANGELOG.md = what changed in each app version ├─ docs\javadoc\ · api-src\ ← the javadoc and the sources of the public API ├─ plugin-guide.en.html ← this document. It sits at the root of the zip ├─ examples\hello\ ← the skeleton of events, a settings card, a tray row and a transformer + test\ — copy from here to start └─ examples\plugin-transformer\ ← changing one app method with java.lang.classfile (advanced)

What you need. JDK 25 and Python 3 (What you need). The tools look for javac in the order --javac → JAVAC → JAVA_HOME → PATH (both build_plugin.py and run_tests.py).

Where to get it. On the Little LUMI SDK downloads page pick the release of the same version as the Lumi you run. Under Assets, take the ZIP whose name starts with LittleLUMI-ModSDK-. After unpacking, check that lib\Shimeji-ee.jar and sdk.json are there. The SDK and the app carry the same version number (currently SDK/app 1.3.0, API 1). A revision that only repackages the docs or the examples keeps its version and is told apart by the build mark at the end of the file name and the commit in sdk.json. What changed in each app version is in docs\CHANGELOG.md.

Compatibility policy. Entries in the API tables are one of two things: stable or experimental. An entry with no mark is stable, and within the same api_version such entries are only added to — they do not disappear and they do not change shape. An entry with the "experimental" chip may still change or disappear, and when it does it is written up in docs\CHANGELOG.md. When api_version goes up, plugins built for the version just before still load for one more version. Doors added in a later version are not in an older app even at the same api_version, so write the app version you tested against into app_version in plugin.json. The full text is "Compatibility policy" in docs\API.en.md.

The terms in one line. Use the SDK only for making Lumi plugins and do not redistribute it; publish the mods you make free of charge only; the rights to the Lumi character, artwork and lines belong to STUDIO LUMI — the full text is LICENSE-SDK.txt inside the zip.

When it ends. After stop(), Lumi collects only what you registered through the context — windows you made yourself, worker threads and prefs().onChange listeners you tidy up in stop() yourself. ask() on a released context returns -2 immediately on the calling thread, and bad every() arguments (null, a period of 0 or less) still throw afterwards. The detailed contract is "Lifecycle" in docs\API.en.md.

If you want to change a decision, start with hooks. Events are "told after it happened", and the decisions inside a feature (whether to stay quiet, which line to pick, how much affection to award) are asked of the hooks first. Only where there is no hook should you reach for a class transformer like examples\plugin-transformer — that is a last resort. The shape of the app classes a transformer touches is outside the compatibility policy, so it breaks when the app updates and that method changes. Several plugins live together — the class path is attached in reverse mod order so a lower mod's transformer registers first, but ServiceLoader's order is not a promise, so do not rely on it.

Changing decisions with hooks

A hook is a place where Lumi asks the plugins before deciding. If an event (ctx.on) is "this just happened", a hook (ctx.hook) is "I am about to do this, is that all right?". The handler receives the value so far as current and returns a new value, or returns null if it has no opinion.

// If a meeting app is in front, always stay quiet (null = no opinion, the app's decision stands)
ctx.hook("focus.quiet", (hook, current, c) -> meetingApp.isForeground() ? Boolean.TRUE : null);
// After 10pm, double the self-talk interval
ctx.hook("selftalk.interval", (hook, current, c) -> LocalTime.now().getHour() >= 22 ? ((Long) current) * 2 : null);
// My image set has no HappyHop, so swap in my own dance
ctx.hook("behavior.force", (hook, current, c) -> "HappyHop".equals(current) && "Neko".equals(c.get("imageSet")) ? "NekoDance" : null);

Five rules. ① The handler runs right there on the thread Lumi called from — keep it cheap and never wait (over 20ms gets a warning). ② When several plugins answer the same hook they are called in mod list order, top to bottom, and the lower one wins (an earlier answer arrives as current). ③ Throwing does not kill the app — only that handler is skipped and it is logged once. A value of the wrong type is ignored too. ④ A promise the user made (an alarm, an errand they pressed themselves, say.txt) cannot be blocked by a plugin through a hook — such places have no hook, or only a "hold" one. What Lumi chooses by herself (self-talk, greetings) can be skipped with "". ⑤ Write "hooks": ["focus.quiet", …] in plugin.json and any hook name the app does not have is reported in the log and on the Mods tab row as "N hook(s) this app does not ask" (it does not block anything from running).

The 15 hooks. focus.quiet (should she stay quiet) · focus.screen_busy (is the screen busy) · text.localized (every bundle string) · sound.effect (the sound effect path, "" = silent) · behavior.force (the behaviour name the director orders) · bubble.duration (how long a bubble lives) · selftalk.line (the self-talk line) · selftalk.interval (the interval) · speech.greeting (the click and chatter greeting) · affection.award (affection being banked) · affection.tier (the tier) · place.allowed (where she may be put down) · bongo.key_frame (the key image slot in Bongo mode) · bongo.key_input (supplying frames from your own input — asked every 40 ms while the bongo is showing) · bubble.text (just before the bubble text — replacement only; an empty answer means the original). The places, arguments, defaults and cautions are in the table in the Mod SDK's docs\API.en.md §5, and where Lumi asks each hook plus its ctx keys are in docs\CATALOG.en.md §3.

Data mods go in fragments

If your mod adds one behaviour, a few lines or a few strings, do not ship a whole behaviors.xml or language_ko.properties. When whole files collide with another mod only one survives, and when Lumi updates and that file changes, the mod's copy takes it back to the old file. Put a fragment instead — put just "what to add" into a folder whose name is the file name with .d after it, and Lumi merges it over the original at startup.

mods\my-dance\ ├─ mod.json ← {"name":"My Dance","version":"1.0.0","app_version":"1.3.0"} — a v1.0.0 chip on the Mods tab ├─ img\Lumi\conf\behaviors.d\dance.xml ← adding one behaviour to Lumi (example below) ├─ img\Lumi\conf\actions.d\dance.xml ← the action that behaviour uses ├─ conf\language.d\my-dance_en.properties ← overriding and adding strings (en only). my-dance.properties fills only missing keys, in every language └─ conf\self_talk.d\my-dance_en.txt ← a few self-talk lines (appended after the original)
img\Lumi\conf\behaviors.d\dance.xml<?xml version="1.0" encoding="UTF-8" ?>
<Mascot xmlns="http://www.group-finity.com/Mascot">
  <BehaviorList>
    <Behavior Name="MyDance" Frequency="10">
      <NextBehaviorList Add="false"><BehaviorReference Name="Fall" Frequency="1"/></NextBehaviorList>
    </Behavior>
  </BehaviorList>
</Mascot>

The rules. ① A fragment is complete XML of the same shape as the original (root <Mascot>). What is inside the lists is appended to the original, and if the same Name already exists it is replaced in place. ② When several mods change the same name, the lower one in the mod list wins. ③ Line fragments are appended after the original, so voice pack numbering does not shift. ④ String fragments apply only to the language at the end of the file name (_ko · _ja · _zh · _zh_TW · _en). ⑤ A broken fragment skips only that file and leaves one line in the log. If the merged result fails the engine's validation, Lumi reads it again without the fragments — a character never disappears. ⑥ Fragments do not count towards "overlaps" on the Mods tab.

Version marking. Put version and app_version in the mod.json at the top of the mod folder (plugin.json for a plugin) and the Mods tab row gets a v1.0.0 chip, and if it differs from the Lumi you are running it says so with a "made for <that version>" chip (it does not block anything).

SymptomThe usual cause → the fix
It says there is no javacNo JDK, or it is not on the PATH. Reinstall JDK 25 (with the options switched on) and open a new command prompt. You can also tell the SDK tools with --javac <where javac.exe is>.
Typing python opens the Store, or "Python was not found"Python is not installed. Install Python 3 from python.org (switch on "Add python.exe to PATH") and open a new command prompt.

Glossary

JDK / JRE
The Java development tools / the runtime. Building needs the JDK; Lumi runs on the JRE (built into Lumi).
jar
A zip file holding a Java program. One plugin = one jar.
class path (-cp)
The list that tells the compiler "the other code this code calls is over here". You write the Lumi jar and lib\* in it.
package
A class's family name. A file that says package hello; has to be in the src\hello\ folder.
ServiceLoader / META-INF/services
The standard Java way of announcing "this jar has this kind of entry point" through a file name. That is what the entry point file is.
EDT
The one and only thread on which Swing draws the screen. Code that touches a window has to run here.
image set
One character. The folder name under app\img\ is the name (Lumi's is Lumi).
overlay
Lumi laying the files in mods\ over app\ at startup. It is how a mod gets installed.

This guide is written for plugin API version 1. When the API version goes up, what is written on this page changes with it.
