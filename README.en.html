Little LUMI Model — Plugin SDK

한국어 · Downloads (Releases)

This repository holds the readable parts only — docs, examples, tools and the public API sources. To build a plugin, download the ZIP from Releases: the lib/ jars you compile against and the generated javadoc live there. This is version 1.5.1.

Welcome. This SDK is the toolkit for adding your own things to Little LUMI: make her react to clicks, head pats and alarms, add lines, menus and hotkeys, or build a mod out of nothing but data — artwork, behaviours, translations.

This distribution is SDK 1.5.1 / app 1.5.1 / api_version 1.

Open index.html for the offline document collection. Code examples have copy buttons; the original Markdown and licence notices are preserved.

In a hurry

With JDK 25 and Python 3 installed, three lines in PowerShell from the unpacked SDK folder:

powershell
python tools\build_plugin.py examples\hello
python tools\run_tests.py examples\hello
Copy-Item -Recurse dist\hello.lumi.sample "<install folder>\mods\hello.lumi.sample"

The first line builds the example into dist\hello.lumi.sample\, the second tests it without the app, the third installs that whole folder. Close the app before you copy and start it again afterwards — a row for the example appears under Settings → Mods. Enable that row's checkbox and agree to the code-execution notice, then quit from the tray and restart the app before expecting its greeting or plugin features. The startup notice's OK button only opens the Mods tab; it does not grant consent. Replacing the JAR requires approval and another restart.

Worth knowing

  • The SDK version is the app version. Pick the SDK that matches the LUMI you run. api_version is a separate API compatibility number. See the release notes for documentation and example revisions.
  • lib\Shimeji-ee.jar is compile-only. It is the Steam build as shipped, so the SDK alone cannot start the app — try your work in your purchased install.
  • A plugin runs inside the app with your rights (no sandbox). Tell the people you share it with.
  • Terms of use are in LICENSE-SDK.txt.

What stays and what may change as the app moves to a new version is written up in API.en.md "Compatibility".

Code mod consent

Installing or subscribing does not authorize execution. Enable the mod's checkbox, review the warning, and agree; code and bundled data are applied on the next app start. Existing last-run hashes are not approval. Changes to any plugin JAR or its plugins/lib libraries require approval again. Creator-declared network/behavior fields are informational, not enforced permissions.

Library JARs must belong to the same approved mod as a plugin; unrelated library-only mods are not placed on the class path. Put dependencies in plugins/lib instead of a JAR manifest Class-Path; manifest class paths and JAR indexes are rejected. The loader uses a verified, protected execution path, so plugins must not rely on their CodeSource path being their install directory.

Code paths containing symbolic links or junctions are unsupported.

When new or changed code mods need approval, a startup notice opens. Its OK button only opens Settings → Mods; it does not grant consent. Review the red Unapproved badge and enable the mod checkbox to give explicit consent.

Declining consent sets the toggle to − (unapproved lock) and suppresses startup reminders for that code version. Click − to return to OFF. Updating a JAR or library clears the lock. Locking never grants consent; code and data remain off. Closing with Escape or X leaves approval and lock state unchanged.
